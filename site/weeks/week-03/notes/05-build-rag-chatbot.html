5. 實作：構建 RAG 聊天機械人

本節定位

  • 上一節：建立了知識庫（資料源）
  • 本節要解決的問題：如何讓 AI「正確使用」知識庫——只根據知識庫回答，遇到不知道的問題誠實拒答？
  • 學完你應該能夠：設定 R-C-C-O 系統提示詞、調校模型參數、測試並發布一個可運作的 RAG 聊天機械人
  • 關鍵詞：系統提示詞、用戶提示詞、R-C-C-O 公式、Temperature、Top_p

知識庫 vs 聊天機械人：分工明確

知識庫只負責「找資料」；聊天機械人負責「決定如何使用資料回答」。

上一節我們建好了知識庫，現在構建一個能基於知識庫回答問題的聊天機械人。如果說知識庫是「教科書」，那聊天機械人就是那個「會翻書並組織答案的學生」——而 System Prompt 決定了這個學生的「考試守則」。

建立聊天機械人

點擊「新建」（New），選擇「對話代理」（Dialogue Agent），輸入應用名稱。

介面配置

配置項說明
AI 模型選取合適的模型（若報錯可改選 DeepSeek V4 Flash 或 Meta Llama）
系統提示詞編寫模型的角色定位、規範與運作指引
數據庫關聯上一節建立的知識庫數據集
檔案上載開啟或關閉允許用户上載文件
開場白設定預設歡迎訊息
語音功能啟用語音播放（TTS）及語音輸入（STT）

模型調校

最大生成長度（Max Tokens）

限制模型單次回覆的最大長度。

溫度值（Temperature）

控制文本生成的隨機度與創意空間。

數值效果適用場景
低（0.1–0.3）高度確定、嚴謹事實為導向的客服場景
中等（0.4–0.6）流暢度與準確度平衡一般對話
高（0.7+）輸出變化多樣創意寫作、發想

核採樣值（Top_p）

  • 調節隨機度的另一核心參數（通常作為 Temperature 的替代）
  • 模型僅在累積概率達到門檻值的詞彙集合中抽樣
  • 典型區間：0.9 至 0.95
客服場景建議：Temperature 設低（0.1–0.3），確保回答事實準確，不「發揮創意」。

系統提示詞 vs 用戶提示詞

理解兩者的區別是構建負責任 AI 的關鍵：

比較項系統提示詞用戶提示詞
目的設定行為、角色、語氣及限制提供即時查詢或任務
持續性靜態；開發者預設，整個對話不變動態；每次互動都變
可見度通常對終端用户隱藏用户直接輸入
權限較高；如同模型的「憲法」較低；必須在系統提示詞框架內運作

R-C-C-O 公式

好的系統提示詞包含四個組件：

組件說明範例
R — 角色（Role）定義 AI 身份與受眾你是一位航空客服助理
C — 核心指令（Core Instruction）定義主要職責根據知識庫回答問題
C — 限制條件（Constraints）設定必須遵守的限制不可使用其他來源；必須引用條款編號
O — 輸出格式（Output format）定義風格與語氣繁體中文、專業簡潔有禮

Prompt 品質檢查表

撰寫完 System Prompt 後，逐項確認：

是否限制了資料來源（只用知識庫，不用外部資訊）？
是否要求引用具體條款或段落？
是否規定「不知道時必須拒答」的明確措辭？
是否指定了輸出語言與語氣？
是否避免讓 AI 處理高風險承諾（如退款、賠償）？

實際測試範例

系統提示詞（航空客服）

你是一位航空公司的客戶服務助理。

規則：
1. 只根據已上載的知識庫文件回答問題，不可以使用其他來源的資訊。
2. 回答時必須清楚指出你依據的文件段落或政策條款編號。
3. 如果知識庫中沒有足夠資料回答問題，必須明確回答：
   「根據現有文件，我無法確認此資訊，建議聯絡客戶服務專員核實。」
   不可以自行推測或編造答案。
4. 所有回覆必須使用繁體中文，語氣專業、簡潔、有禮。

測試問題與預期結果

#測試問題預期結果
1喪親優惠票申請需要準備甚麼文件？AI 引用知識庫政策條款，列出具體所需文件
2我已經完成行程，可以追溯申請退款？AI 引用政策説明完成行程後不可追溯
3香港最大的商場在哪裡？AI 回覆「無法確認此資訊，建議聯絡客戶服務專員」

問題 3 是關鍵測試：它不在知識庫範圍內，AI 應該拒絕回答而不是編造答案。這正是 Klarna 與 Air Canada 的根本差異——前者約束在知識庫內，後者讓 AI 自由發揮。

發布上線

  • 點擊「儲存並發布」（Save and Publish）
  • 選擇發布渠道：免登入窗口、API、Lark/DingTalk/WeChat 等
  • 點擊「建立新連結」設定有效期限
  • 點擊「開始使用」複製分享連結

積分扣除機制

  • 積分從開發者帳戶扣除，不是使用者
  • 開發者可追蹤使用者提問與 AI 回覆記錄
  • 調用次數直接消耗開發者積分配額
Checkpoint 5：用測試問題 1–3 分別測試你的聊天機械人，問題 3 必須回覆「無法確認」而非編造答案。

完成檢查

我能區分系統提示詞和用戶提示詞的職責
我能用 R-C-C-O 公式撰寫一個客服系統提示詞
我能通過 Prompt 品質檢查表的全部五項
我的聊天機械人能通過三個測試問題（含拒答測試）

思考題

  • 如果你的 AI 在測試問題 3（知識庫外問題）時，沒有說「無法確認」而是編造了答案，你會調整哪一個設定？
  • 為什麼系統提示詞被稱為模型的「憲法」？如果用戶輸入的指令與系統提示詞衝突，應該聽誰的？

下一節預告：這個機械人能處理一般查詢，但如果有人問退款問題呢？退款涉及金錢，不能讓 AI 自由回答。下一節我們用 Chatflow 架構，把高風險業務硬隔離開來。
